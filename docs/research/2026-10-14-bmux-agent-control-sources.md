# Bmux agent control: primary-source findings

Research date: 2026-10-14. This note distinguishes upstream behavior from proposed Bmux design. Official source snapshots inspected: T3 Code [`9a5dc756`](https://github.com/pingdotgg/t3code/tree/9a5dc75648de725c737069379600570e391ec8b5), cmux [`62f5cb2b`](https://github.com/manaflow-ai/cmux/tree/62f5cb2bb5639e7b62879ebed18432fd3fa342ec). These are source snapshots, not claims about an installed release. No upstream code was copied.

## Confirmed T3 Code patterns

- **Execution has one owner.** Its environment server owns provider processes, terminals, Git and files; clients control that environment through authenticated RPC. Provider differences belong behind adapters. The v2 orchestrator serializes command decisions without external I/O. EventSink commits events, projections, command receipts and outbox effects together; workers perform effects afterward. Acknowledgement means intent committed, not that execution finished. Checkpoints use hidden Git refs; restoring files must coordinate with provider conversation rollback. [Architecture](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/internals/overview.md)
- **Conversation, runtime and turn are separate.** The implemented adapter boundary exposes app-thread, provider-session, provider-thread and provider-turn events, execution nodes, subagents, messages, plans and runtime requests. It provides open/resume, start, steer, interrupt, respond, snapshot, rollback and fork operations. Capabilities describe available behavior; optional per-thread background-work probes prevent sibling work from keeping an unrelated run alive. [ProviderAdapter](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/packages/provider-core/src/server/ProviderAdapter.ts)
- **Actual integration transports differ.** The Codex adapter imports the Codex app-server client and schemas. The Claude adapter imports `query`, fork/session APIs and permission types from the Claude Agent SDK. Those are structured integration boundaries, not screen scraping. [Codex adapter](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts), [Claude adapter](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts)
- **Generic ACP is present.** T3 supports installed local ACP commands and registry agents, prefers ACP v2 preview, and negotiates v1. Local executable arguments are literal, without shell expansion. Native session import depends on advertised listing/import support. ACP does not guarantee separate accounts for separate instances, nor portable native subagent control. Most agents execute and own their tools; showing a reported terminal does not imply T3 can stop it. [ACP guide](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/user/providers-acp.md)
- **Questions and approvals require protocol-specific handling.** Codex asynchronous questions are notifications answered by a new user message; blocking questions retain a live response path. Persisted requests can outlive a turn or process. Native option IDs must survive normalization. A provider unable to roll back its conversation must reject a coordinated revert before filesystem changes. Codex diffs are derived from checkpoints rather than assuming provider diff notifications are authoritative. [Provider constraints](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/internals/providers.md)
- **Worktrees are managed resources.** Cleanup applies only to T3-managed worktrees; active sessions and shared worktrees prevent removal. Keeping local changes is the default. Deletion waits for sessions and terminals to stop. [Project settings](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/user/project-settings.md)
- **PTY retention is bounded and incremental.** Server callbacks append chunks, avoiding full-scrollback copying per callback. Retention caps both lines and bytes; replay disconnects the PTY writer so historical device queries cannot send replies to the current shell. [Terminal runtime](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/internals/terminal-runtime.md)

T3's older orchestration-v2 model documents contain design language (`should`, `must`, proposed shapes). Their useful vocabulary is app-owned identity with provider refs scoped by session/thread, but the implemented adapter and current architecture above are stronger evidence than treating every older diagram as shipping behavior. [Identity design](https://github.com/pingdotgg/t3code/blob/9a5dc75648de725c737069379600570e391ec8b5/docs/orchestration-v2/entity-ids-and-correlation.md)

## Confirmed cmux patterns

- **Control targets concrete resources.** The CLI supplies workspace/surface context through `CMUX_WORKSPACE_ID` and `CMUX_SURFACE_ID`, and uses `CMUX_SOCKET_PATH`. V2 carries newline-delimited JSON request/response envelopes with request IDs and methods for workspace, pane, surface, input and notification operations. [CLI contract](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/cli-contract.md), [V2 protocol](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/v2-api-migration.md)
- **Stable placement identity is distinct from runtime handles.** Catalog reads expose nullable stable surface/workspace IDs alongside current runtime IDs. Restore may change runtime selectors; duplicate live restores receive fresh stable identities. Labels and cwd are not identity. Stable fields promise neither process survival nor conversation resume, and are not new mutation selectors. [Catalog identity](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/surface-catalog-identity.md)
- **Hooks provide status, notifications and resume metadata.** Supported agent hook installers differ by provider; Claude integration uses a wrapper. Notifications route to a workspace/surface and can carry agent kind, completion/permission category and background/subagent context. Attention is an unread state with a jump action; it need not steal focus. [Agent hooks](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/agent-hooks.md), [Notifications](https://cmux.com/docs/notifications)
- **Approvals are native decisions, not typed keystrokes.** Feed bridges Claude permission/question/plan hooks. Stock Codex permission hooks remain non-blocking telemetry because they precede Codex's automatic reviewer. `codex-teams` owns an app-server connection and bridges actual post-review requests. Hook bridge timeout falls back to the native prompt rather than inventing a denial. [Feed implementation guide](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/feed.md)
- **Agent messages do not overwrite the terminal prompt.** Messages use provider hooks, queue while a human question/permission/plan prompt is open, and track queued/delivered/read/failed states. Claude can wake via an asynchronous hook; Codex waits for its next hook and cannot wake an idle session this way. Headless `claude -p`/`codex exec` do not receive these messages. Delivery capabilities are therefore unequal. [Agent messages](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/agent-messages.md)
- **Draft guards have limits worth improving.** CLI tests check `surface.input_state` before text/paste and reject drafts or human dialogs unless forced. Enter/key delivery is allowed over a draft but blocked by a dialog; missing input-state support on older servers allows the write. This is a preflight check, not evidence of an atomic input transaction. [Guard tests](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/cmuxCLITests/CLISendDraftGuardTests.swift)
- **A socket path is not authority.** cmux-only authorization verifies process ancestry or same-UID inherited capability; restrictive owner modes verify peer UID for each command. Telemetry is parsed/coalesced away from UI work; background non-focus commands preserve the user's selected workspace/application. [Authorization source](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/Packages/macOS/CmuxControlSocket/Sources/CmuxControlSocket/Transport/SocketClientAuthorization.swift), [Focus policy](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/skills/cmux-socket-policy/references/threading-and-focus.md)

cmux's first-class harness document is explicitly a **proposal**: discovery, attach/reuse, detach without stopping, and refusal to silently create a second owner after failed attach are useful design ideas, not proof of general harness support. [Harness RFC](https://github.com/manaflow-ai/cmux/blob/62f5cb2bb5639e7b62879ebed18432fd3fa342ec/docs/rfcs/first-class-harnesses.md)

## Proposed Bmux direction

Borrow the boundaries, not T3's TypeScript/Electron stack or cmux's Swift UI. Keep C11-or-newer process/PTY/socket/queue machinery, Lua orchestration/adapters/view policy, SDL3 presentation, and existing Boggart storage/tools. Reuse Venus data structures when an actual bounded registry/queue needs them.

1. **Two honest control levels.** A terminal session can run any argv, including `boggart --tui`, with cwd and inherited Bmux identity. A managed agent additionally implements structured prompt, event, interrupt, approval and resume capabilities. A terminal-only CLI gets terminal controls and optional hooks; unsupported operations stay unavailable.
2. **One Fleet registry for every agent.** Use provider-neutral agent IDs for Boggart, Codex, Claude and other agents, with registration source, adapter, capabilities, owned session, provider-native cursor, worktree and current terminal surface kept separately. Existing scheduled Boggart workers and externally launched agents contribute to the same roster. Bmux's launcher registers immediately; manually started agents register through supported hooks or an explicit registration command using inherited surface identity. Hook absence means an unknown terminal, not a guessed agent. Expiring generation-scoped presence distinguishes an exited agent from an unreachable integration. This common Boggart/Fleet registry is a proposal; upstream hook integrations establish status/session evidence, not compatibility with our current Fleet.
3. **One session owner, multiple views.** Agent/Fleet/Bmux show the same registered agent and owned session where supported. A structured agent does not automatically have an attachable native TUI; do not manufacture one or start a duplicate conversation. Keep direct TUI launch valid independently. Fleet buttons are capability-based: a hooked terminal agent may offer Focus/Resume while a managed adapter also offers Prompt/Interrupt/Approve. Unsupported controls stay unavailable.
4. **Versioned local control API.** Use bounded JSON frames, request IDs, capabilities and subscriptions. Provide register/list/start/attach/status/prompt/interrupt/respond/resume operations. Route every action to agent/session ID plus generation and every approval to request ID plus live response capability. Inject socket/session/workspace/surface context on launch, but verify caller authority independently.
5. **Durable commands and visible outcomes.** Persist accepted intent, then perform asynchronous side effects and record completion/failure. Retries deduplicate by command ID. Model `running`, `waiting_for_approval`, `waiting_for_answer`, `idle`, `failed`, `exited` separately; quiet output does not prove completion.
6. **Protect human input atomically.** Structured prompts queue or steer through the adapter. Terminal injection requires target generation and expected input revision checked by the owner at write time. Unknown draft state cannot justify unattended injection. Explicit interrupt and approval are separate operations, not generic Enter/Ctrl-C macros.
7. **Start with Boggart itself.** Add direct `boggart --tui` launch first. Then expose an opt-in structured event/control endpoint from the Boggart runtime so its TUI remains usable while Bmux sees the same session's status, requests and tools. Add Codex app-server next; generic ACP after the contract is stable. Claude SDK source is a useful reference, but adopting its JavaScript SDK would introduce a runtime decision this C/Lua project has not made.
8. **Worktree/diff review follows ownership.** Offer an existing checkout or an owned worktree, show file diffs and task/branch context, and keep commit/push explicit in the UI. Checkpoint/file restore and conversation rollback must be coordinated and capability-gated. Session restart, conversation resume and reattaching a live process are three different outcomes.

This creates a practical progression: launch real agent TUIs in Bmux; receive trustworthy status/attention; control Boggart sessions structurally; add provider adapters; then add worktree review and session recovery. It does not require remote/cloud control or a second orchestration server before the local path works.
